# Deployment: dev and final

The mod's source lives in `Mod/`. You never edit a copy in the game folder. `deploy.ps1` puts the
mod into `%APPDATA%\SpaceEngineers\Mods` under one of two targets defined in `deploy.json`:

| Target | Local folder | Workshop item | How it's deployed |
|---|---|---|---|
| `dev`   | `missil-misterplace-dev` | [3514275550](https://steamcommunity.com/sharedfiles/filedetails/?id=3514275550) | **Junction** to `Mod/` (live edits) |
| `final` | `missil-misterplace`     | [3496380795](https://steamcommunity.com/sharedfiles/filedetails/?id=3496380795) | **Copy** of `Mod/` at a clean commit |

## Day-to-day (dev)

```powershell
.\deploy.ps1 dev
```

- Creates the junction `Mods\missil-misterplace-dev -> <repo>\Mod`, if it isn't there yet.
- Writes `Mod/modinfo.sbmi` with the dev Workshop ID. The file is git-ignored.
- Safe to run repeatedly; nothing changes when the link already exists.
- Edit files in `Mod/`, then reload the test world. The game recompiles scripts on world load.
- To publish a dev build, use the game's **Mods** screen: select `missil-misterplace-dev` and click **Publish**. It
  updates Workshop item 3514275550 because that's the ID in `modinfo.sbmi`.

## Release (final)

```powershell
git status                   # must be clean
.\deploy.ps1 final -DryRun   # preview what will happen
.\deploy.ps1 final
```

- Refuses to run if the working tree has uncommitted changes, so every release maps to a commit.
- Moves the existing `Mods\missil-misterplace` folder to `%APPDATA%\SpaceEngineers\ModBackups\`.
- Copies `Mod/` there and writes `modinfo.sbmi` with the final Workshop ID.
- Tags the commit `release/<yyyy-MM-dd_HHmm>`. `release/baseline` marks the version that was
  published before the repo existed.
- Then publish `missil-misterplace` from the game's Mods screen.

To see what's unreleased since the last release:

```powershell
git log --oneline (git describe --tags --abbrev=0 --match "release/*")..HEAD
```

## Rules

- **Never load dev and final in the same world.** Both versions define the same block and ammo subtypes, run
  the same session component, and use the same network channel (`GuidedMissileSystem.NetworkId` is
  derived from the final Workshop ID). The result would be duplicated logic and packets.
- Block mods (SLBM, LauncherX, IronDomeX) must list the brain as a **Required item** on the Workshop:
  dev block mods require the dev brain, and final block mods require the final brain.
- Backups in `ModBackups/` are never deleted automatically. Clear old ones out by hand.

## Files

| File | Purpose |
|---|---|
| `deploy.json` | Steam owner ID plus a local folder and Workshop ID per target |
| `deploy.ps1` | Deploy script (Windows PowerShell 5.1+) |
| `Mod/modinfo.sbmi` | Generated by `deploy.ps1 dev`; git-ignored |

## Targets that are not published yet

If a target's `workshopId` in `deploy.json` is `null` (for example SLBM's dev target), `deploy.ps1` writes a
`modinfo.sbmi` without an ID, so the first **Publish** creates the Workshop item. It never reuses another
target's ID, and it keeps an ID the game wrote itself. After the first publish, copy the new ID from
`Mod/modinfo.sbmi` into `deploy.json` and commit.

## Dependencies between mods

Space Engineers has no file-based mod dependency, so it is enforced in three places:

1. **`requires` in `deploy.json`** (for example LauncherX requires `missil-misterplace`). `deploy.ps1` warns, and never
   fails, when the required mod's folder for the same target (dev or final) is not in the Mods folder.
2. **A runtime check** in the dependent mod's script, where it matters: LauncherX logs and shows a notification at world
   start if the brain is not in the world's mod list (by Workshop ID 3496380795/3514275550, or by local folder name).
3. **Workshop "Required items"** (manual, on the Steam page): the dev item must list the dev brain and the final item the
   final brain. This is what makes players subscribe to both. It cannot be done from the repo.

Always enable both mods in the world. Never mix dev and final.
